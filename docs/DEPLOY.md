# Deploying the API

Private testing runs on the API on **Render** and Postgres on **Neon**, DNS wherever `oskeylabs.com` lives. The web app is on Vercel; see `docs/DEPLOY.md` in the web repo. Both started in Ohio (`us-east-2`); `render.yaml` now describes a Starter service in **Frankfurt**, next to a Neon project in AWS Europe Central 1, the closest region to Nigeria that either offers (neither has Africa, Render has no London). The move is click by click in `docs/LAUNCH.md` at the project root, "Moving to Frankfurt".

| | Testing address |
|---|---|
| Web app | `https://forum.oskeylabs.com` |
| API | `https://api.forum.oskeylabs.com` |
| Cookies | `COOKIE_DOMAIN=.forum.oskeylabs.com`, so both hosts share the sign-in cookies |

The `forum` label is neutral on purpose: when the name is picked, the site moves to its own domain and only the settings in this file and the web app's change.

## How a deploy happens

1. A PR merges to `main`. CI runs (typecheck, tests, build).
2. When CI passes, `.github/workflows/deploy.yml` runs `prisma migrate deploy` against Neon's **direct** (non-pooled) host, then calls Render's deploy hook.
3. Render builds (`npm ci --include=dev && npm run build`), starts `npm start`, and switches traffic once `/v1/health` answers.

Migrations run before the new code starts, so a migration must work with the old code too (add columns before using them; drop them a release later). Render's auto-deploy is off so it can't race the migration. To redeploy by hand: Actions → Deploy → Run workflow.

## One-time setup

1. **Neon:** in the project, turn on point-in-time restore (the free plan keeps a short history window) and copy two connection strings: the pooled one (host has `-pooler`) and the direct one (same string without `-pooler`).
2. **Render:** New → Blueprint → pick `Femosky/project-forum-backend`. It reads `render.yaml`. Fill in the variables marked below. JWT_SECRET is generated for you.
3. **Render deploy hook:** service → Settings → Deploy Hook → copy the URL.
4. **GitHub secrets** (repo → Settings → Secrets and variables → Actions): `DIRECT_DATABASE_URL` (direct Neon URL) and `RENDER_DEPLOY_HOOK_URL`.
5. **Custom domain:** Render service → Settings → Custom Domains → add `api.forum.oskeylabs.com`, then add the CNAME it shows (`api.forum` → `forum-api.onrender.com`) at the DNS host. On Cloudflare, leave the record **DNS only** (grey cloud) so Render can issue the certificate.
6. Run the Deploy workflow once by hand, then open `https://api.forum.oskeylabs.com/v1/health`.

## Analytics

Events go from the API to PostHog's batch endpoint every 10 seconds (`src/lib/analytics.ts`). There is no tracking script and no cookie. Events carry the account id (or `guest`), never content, post or comment ids, and anonymous posts are sent without their community.

| Event | When | Properties |
|---|---|---|
| `signup` | account created | `method` (`email`, `google`) |
| `user_active` | a signed-in request, once per account per day | |
| `post_created` | post submitted | `type`, `anonymous`, `community` (not for anonymous posts), `held` |
| `comment_created` | comment or reply | `reply`, `anonymous`, `held` |
| `vote` | vote changed | `target`, `value` |
| `search` | first page of a search | `type`, `query` (lowercased), `results`, `no_results` |

Page views and shares come from the web app. Return visits (D1/D7/D30) are a PostHog Retention insight: first event `signup`, returning event `user_active`.

## Admin panel accounts

The admin panel (`/admin`) uses staff accounts, separate from forum accounts, with a password and an authenticator app (two-factor) for everyone. After the deploy that adds them, create the first owner once, from Render → forum-api → **Shell**:

```
npm run admin:create-owner -- --email you@example.com --name "Your name"
```

It prints a temporary password. Sign in at `https://forum.oskeylabs.com/admin/login`, scan the QR code with an authenticator app, save the recovery codes, then choose a new password. Invite everyone else from Admin → Admins. The old forum-account admin role no longer opens the panel.

## Jobs

pg-boss (on the same Postgres) runs emails, link previews and two schedules, on Lagos time:

| Job | When | What |
|---|---|---|
| `trending.compute` | every 10 minutes | Trending posts, rising communities and topics (`src/modules/trending`), plus the "Did you mean" word list hourly |
| `stats.daily` | 00:20 | Yesterday's `DailyStat` and `CommunityDailyStat` rows, and old visitor salts deleted |

**Idle suspend (Neon's free plan has 100 compute hours a month).** Neon suspends the database after 5 minutes without queries and bills nothing while suspended. The API sends none while idle: `/v1/health` (what uptime monitors ping) doesn't touch the database, the view/visit buffers write only when something was counted, idle pool connections are closed after 10 seconds without keep-alives, and the job queue (which polls every 10 seconds and does housekeeping every 10 minutes while running) stops after `JOBS_IDLE_SUSPEND_MINUTES` without requests. The next request starts it again, refreshes a stale trending snapshot and writes any missed daily stats; a job queued while it's stopped starts it first, so nothing is lost. Measured locally (29 Oct, a health ping every minute): the queue stopped 5¼ minutes after the last real request and from then on the API held no database connections and sent no queries; the only activity left was Postgres's own background work (about 2 transactions a minute, none from the API). An open, signed-in tab in the foreground polls the unread-notification count, which counts as a request and keeps the database awake.

With `JOBS_ENABLED=false` nothing is scheduled. `GET /v1/trending` then recomputes a snapshot older than 10 minutes (the first read waits; later ones get the current snapshot while it refreshes) and Admin → Stats writes any missing days when opened, so both keep working without keeping Neon awake.

## Site metrics

For Admin → Stats and advertiser decks, without Redis or a tracking script:

- **Views, visits, last active**: counted in memory and written every `METRICS_FLUSH_SECONDS` with one statement per table (`src/modules/metrics/buffer.ts`), and on shutdown. Every write adds or inserts-if-missing, so several instances stay correct. A crash loses at most one interval.
- **Unique visitors**: the browser sends `POST /v1/metrics/visit` after each page (so CDN-cached pages count). A visitor is `sha256(day's salt, IP, user agent)`; the salt is random per Lagos day and deleted after two days, so ids can't be linked across days or recomputed. IPs are never stored. Bots (by user agent) are skipped.
- **DAU/WAU/MAU**: accounts with a signed-in request that day (`DailyActiveUser`), and `User.last_active_at` moves at most every 15 minutes.

## Ads pointing at localhost

Ad links that lead to this site (`/communities`, or a link to `WEB_URL`) show the site's name and redirect to `WEB_URL` plus the path, and so do leftovers pointing at a local test server, so a test campaign saved with `http://localhost:3000/...` no longer shows "localhost". In production the admin panel only accepts public `https://` links or site paths starting with `/`. To list affected rows (read-only; run it in Neon's SQL editor):

```sql
SELECT c."name" AS campaign, c."kind", c."status", a."id" AS creative_id, a."headline",
       a."click_url", a."image_url", adv."name" AS advertiser, adv."website", adv."logo_url", c."payment_url"
FROM "AdCreative" a
JOIN "Campaign" c ON c."id" = a."campaign_id"
JOIN "Advertiser" adv ON adv."id" = c."advertiser_id"
WHERE concat_ws(' ', a."click_url", a."image_url", adv."website", adv."logo_url", c."payment_url")
      ~* '(localhost|127\.0\.0\.1|0\.0\.0\.0|\[::1\]|\.local(/|:|$)|//10\.|//192\.168\.|//172\.(1[6-9]|2[0-9]|3[01])\.)';
```

Fix a row in Admin → Ads (edit the creative's link, e.g. to `/communities`) rather than in SQL.

## Backups

`.github/workflows/backup.yml` runs every Sunday at 03:00 UTC (and on demand: Actions → Backup → Run workflow). It dumps the database over the direct connection, restores the dump into a scratch Postgres 17 and compares tables and row counts (`scripts/backup-check.sh`), then encrypts it with `BACKUP_PASSPHRASE` and keeps it as a workflow artifact for 35 days. The repo is public, so the dump is never stored unencrypted. A failed run emails you.

Needs the repo secrets `DIRECT_DATABASE_URL` (already set for deploys) and `BACKUP_PASSPHRASE` (a long random string; keep a copy in your password manager, because without it the backups can't be opened).

Neon's own restore history covers "undo the last few hours"; these weekly dumps cover losing the Neon project itself.

To restore:

1. Actions → Backup → pick a run → download the artifact and unzip it.
2. `gpg --decrypt forum-db-YYYY-MM-DD.dump.gpg > backup.dump` (asks for the passphrase).
3. In Neon, create an empty database or branch to restore into, and copy its direct URL.
4. `pg_restore --no-owner --no-privileges --dbname="<direct URL>" backup.dump` (pg_restore 17 or newer).
5. Point `DATABASE_URL` on Render (and the GitHub secret) at it once it looks right.

## Free-tier notes

- On the free instance (the original Ohio setup): Render sleeps after 15 minutes without traffic and takes about a minute to wake. An uptime monitor on `/v1/health` every 5 minutes keeps it awake (750 free hours a month covers one service) without touching the database, so Neon still scales to zero.
- Neon's free plan has a monthly compute allowance. With jobs inline and the pooler in front, the database only runs while people use the site.
- Moving to a paid host for public launch is a settings change: same build and start commands, same variables.
